# Проверка доступности доменов и их истории

## 1. Цель

Создать консольный Python-скрипт, который:

1. получает список основ доменных имён, например `chat`, `livesupport`, `helpdesk`;
2. комбинирует их с заданными зонами, например `.ru`, `.com`, `.net`, `.org`, `.io`;
3. проверяет, зарегистрирован ли каждый домен и можно ли его зарегистрировать сейчас;
4. только для доменов, доступность которых подтверждена, ищет исторические признаки прежнего использования;
5. сохраняет результаты в машиночитаемом и удобном для просмотра виде.

## 2. Важное ограничение

RDAP и WHOIS показывают главным образом **текущее состояние**. Если домен был удалён и снова стал свободным, бесплатный RDAP/WHOIS обычно не сообщает дату его первой регистрации.

Следует различать:

- `current_creation_date` — дата начала текущей регистрации;
- `historical_registration_date` — дата регистрации из исторической WHOIS-базы;
- `earliest_web_capture` — первая найденная копия сайта в веб-архиве;
- `earliest_observed_date` — самая ранняя дата любого найденного исторического сигнала;
- `history_status` — итоговая оценка наличия истории.

Первая запись в веб-архиве, Certificate Transparency или passive DNS **не является доказанной датой первой регистрации**. Скрипт не должен выдавать её за таковую.

## 3. Источники данных

### 3.1. Текущая регистрация

Основной источник — авторитетный RDAP-сервер зоны, найденный через IANA RDAP Bootstrap:

- `https://data.iana.org/rdap/dns.json`
- стандарт поиска сервера: RFC 9224;
- ответ `200` с объектом `domain` означает, что домен присутствует в реестре;
- `404` или иной предусмотренный `4xx` означает только, что запись не найдена в этом RDAP-сервисе.

Для зон без RDAP нужен адаптер официального WHOIS соответствующего реестра. Для `.ru` и `.рф` — WHOIS Технического центра Интернет / Координационного центра.

DNS-запрос нельзя использовать как единственный способ проверки: зарегистрированный домен может не иметь DNS-записей.

### 3.2. Реальная возможность регистрации

Финальное подтверждение доступности должен давать API регистратора, который поддерживает нужную зону и возвращает состояние покупки/регистрации. Это отдельный слой `AvailabilityProvider`.

RDAP/WHOIS используется как независимый источник текущего регистрационного состояния, но не как окончательная гарантия покупки.

### 3.3. История свободного домена

Источники располагаются по уровню доказательности:

1. подключаемый платный Historical WHOIS API — лучший источник прежних регистраций;
2. Internet Archive CDX — дата первой сохранённой веб-страницы;
3. Certificate Transparency — самый ранний публичный сертификат;
4. подключаемый passive DNS API — самая ранняя наблюдавшаяся DNS-запись.

Исторические провайдеры должны быть опциональными. Отсутствие API-ключа не должно ломать основную проверку.

## 4. Входные данные

Поддержать:

- текстовый файл: одна основа имени на строку;
- CSV с колонкой `name`;
- зоны из CLI или конфигурационного YAML-файла;
- полные домены во входном файле как отдельный допустимый режим.

Пример:

```text
chat
livesupport
helpdesk
```

Пример запуска будущего скрипта:

```powershell
python domain_checker.py check --input names.txt --zones ru,com,net --output results
```

## 5. Нормализация и валидация

Для каждой строки:

1. удалить пробелы, ведущую точку зоны и завершающую точку FQDN;
2. привести ASCII-часть к нижнему регистру;
3. преобразовать IDN через IDNA в A-label/Punycode для сетевых запросов;
4. проверить допустимые символы, длину метки и полную длину домена;
5. удалить дубликаты после нормализации;
6. сохранить и исходное, и нормализованное значение;
7. не выполнять запросы для невалидных имён, а записывать понятную причину.

## 6. Статусная модель

Не использовать простое булево поле `available`.

### `registry_status`

- `registered` — домен найден в авторитетном RDAP/WHOIS;
- `not_found` — запись не найдена;
- `unknown` — источник недоступен, ограничил запросы или ответ неоднозначен;
- `invalid` — имя не соответствует правилам.

### `availability_status`

- `available` — API регистратора подтвердил возможность регистрации;
- `premium_available` — регистрация возможна по премиальной цене;
- `registered` — зарегистрирован;
- `reserved` — зарезервирован или запрещён;
- `unsupported_tld` — провайдер не поддерживает зону;
- `unknown` — достоверный ответ не получен.

### `history_status`

- `confirmed_registration_history` — исторический WHOIS подтвердил прежнюю регистрацию;
- `web_or_dns_history_only` — есть косвенные следы, но регистрация исторически не подтверждена;
- `no_history_found` — подключённые источники ничего не нашли;
- `not_checked` — история не проверялась;
- `unknown` — проверка не завершилась достоверно.

## 7. Алгоритм

1. Загрузить конфигурацию, входные имена и секреты из переменных окружения.
2. Нормализовать имена, раскрыть декартово произведение `имена × зоны`, убрать дубликаты.
3. Загрузить и локально закешировать IANA RDAP Bootstrap с TTL.
4. Для каждого домена определить RDAP endpoint по правилу longest match.
5. Выполнить текущую регистрационную проверку:
   - RDAP;
   - при отсутствии RDAP — разрешённый для зоны WHOIS-адаптер;
   - разобрать даты, статусы, регистратора и nameserver-ы;
   - сохранить сырой ответ или его безопасный диагностический фрагмент.
6. Независимо запросить `AvailabilityProvider`, если он настроен:
   - подтвердить возможность регистрации;
   - получить обычную или премиальную цену, валюту и период;
   - классифицировать зарезервированные и неподдерживаемые имена.
7. Свести ответы:
   - RDAP `registered` всегда запрещает классификацию `available`;
   - registrar `available` + registry `not_found` даёт высокую уверенность;
   - противоречие переводит результат в `unknown/conflict`, сохраняет оба ответа;
   - одно только `not_found` не превращается в `available`.
8. Запускать исторический конвейер только при `availability_status in {available, premium_available}`:
   - Historical WHOIS;
   - Internet Archive;
   - Certificate Transparency;
   - passive DNS, если подключён;
   - вычислить минимальные даты отдельно по типам источника.
9. Рассчитать `confidence` и список `evidence`, не смешивая доказанные даты с косвенными.
10. Записать результат сразу после каждого домена в SQLite/JSONL, чтобы процесс можно было продолжить после остановки.
11. После завершения экспортировать CSV и итоговый JSON.
12. Вывести краткую сводку: всего, доступно, premium, занято, зарезервировано, неизвестно, с подтверждённой и косвенной историей.

## 8. Поведение при ошибках и лимитах

- асинхронность с отдельным лимитом параллелизма на каждого провайдера;
- общий и per-host rate limit;
- `Retry-After` для `429`;
- exponential backoff с jitter для временных `5xx`, timeout и сетевых ошибок;
- ограниченное число повторов;
- circuit breaker для систематически падающего endpoint;
- кеширование успешных и отрицательных результатов с разным TTL;
- resumable-запуск;
- корректное завершение по `Ctrl+C`;
- никакого бесконечного повтора;
- User-Agent с названием приложения и контактным адресом из конфигурации;
- соблюдение условий использования каждого API.

## 11. Критерии готовности

1. Один сбой провайдера не останавливает весь пакет.
2. `404 RDAP` никогда сам по себе не маркируется как гарантированно доступный домен.
3. Для свободного домена дата Wayback не называется датой первой регистрации.
4. Повторный запуск использует кеш и продолжает незавершённую работу.
5. Поддерживаются Unicode/IDN и Punycode.
6. CSV корректно открывается в Excel: UTF-8 BOM, плоские значения, даты ISO 8601.
7. Есть unit-тесты всех ветвей сведения статусов.
8. Интеграционные тесты используют фикстуры/моки и не расходуют квоты.
9. Реальные сетевые smoke-тесты отделены и запускаются только явным флагом.
10. README объясняет разницу между регистрацией, доступностью покупки и историческими следами.

# Инженерный промт для реализации

Ты — ведущий Python-инженер. Реализуй production-ready CLI-приложение для пакетной проверки доменных имён согласно спецификации ниже. Не упрощай модель результата до `занят/свободен`: система обязана различать текущее присутствие в реестре, подтверждённую возможность регистрации и исторические признаки.

## Задача

Приложение получает список основ (`chat`, `livesupport`) и список TLD (`ru`, `com`, `net`), строит домены, проверяет текущую регистрацию, подтверждает возможность покупки через настраиваемый registrar API и для подтверждённо доступных доменов ищет историю.

## Непереговорные правила

1. Для gTLD и поддерживаемых ccTLD находи авторитетный RDAP через IANA Bootstrap `https://data.iana.org/rdap/dns.json` по RFC 9224.
2. Не считай DNS/NXDOMAIN доказательством доступности.
3. Не считай RDAP/WHOIS `not found` гарантией возможности регистрации.
4. Финальный `available` разрешён только после положительного ответа `AvailabilityProvider`.
5. Если RDAP говорит `registered`, а registrar API — `available`, верни конфликт/`unknown`, не скрывай расхождение.
6. Для `.ru`/`.рф` предусмотрен отдельный официальный WHOIS-адаптер, используемый при отсутствии подходящего RDAP.
7. Историю проверяй только для `available` и `premium_available`.
8. `current_creation_date`, historical WHOIS date, Wayback date, CT date и passive DNS date храни отдельно.
9. Никогда не называй Wayback/CT/passive DNS датой первой регистрации.
10. Не хранить API-ключи в репозитории, логах, SQLite или экспортных файлах.

## Реализация

- Python 3.12+, typed code.
- CLI на Typer.
- HTTP через `httpx.AsyncClient`.
- Pydantic-модели результата и настроек.
- Интерфейсы/Protocol для всех провайдеров, dependency injection.
- Ограниченная асинхронность, отдельный rate limiter на host/provider.
- Retries только для временных ошибок, поддержка `Retry-After`, exponential backoff + jitter.
- SQLite checkpoint/cache и потоковая запись JSONL.
- Экспорт CSV с UTF-8 BOM и итогового JSON.
- YAML-конфигурация плюс env vars для секретов.
- Структурные логи без секретов.
- Команды минимум:
  - `check`;
  - `resume`;
  - `export`;
  - `providers`;
  - `validate-config`.
- Флаги `--dry-run`, `--offline-fixtures`, `--force-refresh`, `--concurrency`.

## Провайдеры

Реализуй:

1. `IanaBootstrapProvider`;
2. `RdapProvider`;
3. `RuWhoisProvider`;
4. абстрактный `AvailabilityProvider` и один конкретный адаптер, выбранный только после проверки актуальной официальной документации API;
5. абстрактный `HistoricalWhoisProvider` с корректным поведением без ключа;
6. `WaybackProvider`;
7. `CertificateTransparencyProvider`;
8. опциональный интерфейс `PassiveDnsProvider`.

Если бесплатного достоверного Historical WHOIS API нет, не имитируй его и не делай scraping сторонних сайтов. Оставь чистый адаптер с конфигурацией для легального API и явно обозначь ограничение в README.

## Сведение данных

Создай чистую детерминированную функцию reconciliation, покрытую табличными тестами. Она принимает ответы registry и registrar, возвращает:

- `registry_status`;
- `availability_status`;
- `confidence`;
- `conflict_reason`;
- массив evidence с источником, временем запроса и безопасной выдержкой.

Основные ветви:

- registry=registered → registered;
- registry=not_found + registrar=available → available;
- registry=not_found + registrar=premium → premium_available;
- registry=not_found + registrar=reserved → reserved;
- registry=unknown или registrar недоступен → unknown;
- любое противоречие → unknown/conflict.

## Тестирование

Сначала создай тестовые фикстуры, затем реализацию.

Обязательно покрыть:

- ASCII, Unicode и IDN;
- невалидные метки;
- IANA longest-match;
- RDAP 200, 404, 429, 5xx, timeout, malformed JSON;
- WHOIS `.ru` с `REGISTERED`, свободным доменом и изменившимся форматом;
- reserved/premium/unsupported;
- все конфликты reconciliation;
- Wayback без снимков и с несколькими снимками;
- отсутствие API-ключей;
- остановку и resume;
- CSV с русским текстом;
- удаление секретов из логов;
- кеш TTL и `--force-refresh`.

Интеграционные тесты по умолчанию полностью офлайн через `respx`/fixtures. Реальные запросы допускаются только отдельным явным флагом и не должны запускаться в CI.
